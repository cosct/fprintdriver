# 四份实现对比与 EH575 驱动架构决策

## 1. 架构总览

| 维度 | topni1 egis0575 | Animeshz patch (2021) | championswimmer egis0577 (b19955e) | python |
|---|---|---|---|---|
| libfprint 类 | `FpImageDevice` | `FpImageDevice` | **`FpDevice`（纯设备）** | 无（open-fprintd D-Bus） |
| 扫描模型 | swipe（10 帧拼接） | swipe（8 帧） | **press（单帧/触按）** | press（单帧） |
| 匹配算法 | NBIS Bozorth3（bz3=15） | NBIS Bozorth3（bz3=15） | **自研 NCC（12 帧画廊）** | OpenCV |
| 初始化 | 校准读+上传（5 相位） | PRE_INIT/POST_INIT 表 | PRE_INIT/POST_INIT 表 | 独立第三套序列 |
| 真机状态 | **EH575 已装可用**（用户机器） | 未完成 | **EH577 可用**（enroll/verify/KDE 解锁） | 半稳定 |

## 2. 为什么 swipe 模型是 7 月精度问题的根源

1. 传感器 103×52（有效可能仅 70×52），swipe 条带之间靠运动估计拼接——
   小条带的运动估计误差被放大，拼接图畸变直接摧毁 minutiae 提取
2. Bozorth3 在如此小的图像上本来就不可靠（EH577 作者实测结论：NBIS unusable，
   匹配分数不稳定）
3. swipe 要求用户"长划整个指尖"，笔记本电源键大小的传感器上体验极差，
   划得快/慢/歪都影响成帧

EH577 的解法证据链：press 单帧 + 背景扣除 + 质量门控 + NCC 画廊匹配，
在真实硬件上做到 KDE 解锁可用。

## 3. championswimmer b19955e 的关键机制（移植清单）

### 采集（每次轮询一个完整新鲜周期）
- PRE_INIT(29) → POST_INIT(17) 末包 `64 14 ec` 收帧
- 无 REPEAT 表轮询——每帧都从 POST_INIT 走（牺牲速度换稳定，配合 claim 配额）
- claim 回收：`MAX_FRAMES_PER_CLAIM=6`，达到即 release+re-claim 接口
- 启动加固：claim 后 settle 150ms；首包超时 → claim 回收重试 ≤2 次 → 干净失败
- 超时统一 2000ms（不是 topni1 的 10s）

### 指纹在检（软件）
- 暖背景基线：启动先收 3 个有效空帧（BACKGROUND_WARMUP_FRAMES=3），
  否则热像素 idle 帧会被误判为手指（死锁坑）
- 基线滚动更新：最近的"无指"帧持续覆盖
- 判据：bg 扣除后 `val > bg+2` 为活动像素；coverage = 活动像素(>15)占比，
  intensity = 活动像素均值
  - 存在：coverage ≥18% 且 intensity ≥10
  - 可用：coverage ≥25% 且 intensity ≥20

### 每触按（turn）状态机
- settle 400ms（手指按下稳定后才评估）
- turn 超时 1400ms（单次按压绝不无限轮询）
- 质量门控通过的帧立即提交（fast exit）；否则记"最优帧"（饱和像素最少）
- 录入阶段每次 accepted 后 800ms re-arm 封锁（强制真实抬手）

### 图像处理管线（顺序）
1. 裁剪有效区 70×52（死区列不参与任何计算）
2. 暖背景扣除（`val > bg+2 ? val-bg : 0`）
3. pad 宽度到 4 的倍数（72）→ `fpi_image_resize` 2x → **144×104**
4. 3×3 中值降噪（去高频噪点，保边缘）
5. stretch5 对比度拉伸：p5..p99 → 20..245
6. Stage-2 质量门控（全部通过才接受）：
   - grain < 6.000%（中值滤波残差 >25 的像素占比，×1000 存储）
   - 0 < minutiae < 10（NBIS get_minutiae；上限防噪点制造假细点）
   - ridge pixels > 4000（阈值 180 以下计为脊线）
   - （stretch5 本身不是门控，只是增强）

### NCC 匹配器
- 录入：12 帧画廊（FPI_PRINT_RAW，GVariant `(uu aay)` 存入 fpi-data）
- 验证：probe 帧对画廊每帧做峰值 NCC（搜索窗 ±30px），`best ≥ 0.50` 且
  `hits ≥ 2` 判匹配
- 无 identify（`FP_DEVICE_FEATURE_IDENTIFY` 显式关闭）
- `temp_hot_seconds = -1`

## 4. EH575 移植决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 基座架构 | championswimmer press+NCC | 唯一在真实小图传感器上验证可用的匹配路线 |
| 初始化 | topni1 校准流程 | EH575 真机验证；EH577 无校准能跑可能是个体差异，EH575 保守起见保留；后续可实验去掉 |
| 有效宽度 | **真机验证后定**（70 或 103） | 两源矛盾，帧统计 5 分钟出结论 |
| swipe/press | press | §2 |
| claim 配额/回收 | 移植（6/claim + 回收） | 防死锁，EH575 未见反例报告但风险对称 |
| settle/turn 时序 | 移植（400/1400ms） | 已调好的真机参数 |
| Stage-2 门控 | 移植后在 EH575 数据集上重调 | 阈值与传感器噪声特性耦合 |

## 7. 匹配器实验终局（2026-09-12 深夜，带完整数据）

七个匹配方案在同一数据集（同一人左右食指、位置多样画廊、多帧 probe）
上全部无法区分真假：

| 匹配器 | 真手指 best 分数 | 冒充 best 分数 | 结论 |
|---|---|---|---|
| NCC（±30 窗，多帧最佳） | 0.36–0.96 | 0.38–0.80 | 重叠，冒充可高至 0.80 |
| 掩码 NCC（非零并集） | 0.36–0.67 | 0.38–0.70 | 与普通 NCC 无差异 |
| Bozorth3（2x，4–10 细点） | ~0 | 0–7 | 细点太少，共识匹配失败 |
| Bozorth3（4x，54 细点） | 0 | 0–7 | 细点为增强伪影，帧间不可重复 |
| POC / BLPOC | 0.05–0.29 | 0.04–0.34 | 完全重叠 |
| 方向场（结构张量块方向） | 0.023–0.026 | 0.019–0.026 | 完全重叠 |
| SigFM（SIFT+Lowe+几何投票） | — | — | 跨按压 Lowe 通过仅 2–4 对（<5 下限）；自匹配 3.5 亿票证明移植正确 |

**根因（原始帧统计实证）**：按压帧原始灰度 std 仅 3.0（空帧 2.7）——
脊线可见度完全由驱动管线（背景扣除+拉伸）合成，原始信号信噪比极低。
一切依赖"自然纹理可重复性"的描述子（SIFT/细点）都没有原料；一切
全局相关性（NCC/POC）又被同人食指的结构相似性淹没。

**剩余可行方向**：
1. **【新主线】移植 Windows 引擎（2026-09-13 从反编译源码完整还原了其架构）**：
   - 增强：103×52→176×88（1.75x 加权重采样）+ 12×12 块前景掩码 +
     平场归一化（半径 5 模糊除法）+ **按脊线周期选系数的 FIR 滤波器组**
     （系数表在 EgisTouchFPEngine0575.dll 数据段：UNK_180043070 起，
     长度表 DAT_180041b50；atan2 表 DAT_1800433c0；描述子权重 DAT_1800431d0）
   - 特征：滤波响应 3×3 严格局部极大值（>1000）→ 非极大抑制（0.75×周期²）→
     亚像素细化 → 梯度方向（整角度 0..360）→ 11×11 梯度方向直方图二值描述子
     （质量分 3/6/8 档 = 24/48/64 字节）
   - 匹配：popcnt 海明最近邻（预算 115/512 bit）→ 中值平移 + 角度一致性
     （7°/8px）→ ≥5 对一致；score=Σ(0x80−海明)，阈值 660，自适应阈值
     （失败 −80 / 成功 +60 封顶 1.5x）
   - 约束：每图最少 11 特征；录入 ~14 按压 + 重复拒收 + 模板合并（≤4096 特征）
   - 验证时回馈更新模板（加密注册表 blob 'AE'，密钥 DAT_180038248）
   - 障碍：需要原始 EgisTouchFPEngine0575.dll 提取系数表（Ghidra 工程的
     idata 不含直接可读二进制；RizinCutter 只有另外两个 DLL 的 rzdb）；
     获取途径 = Acer 官方 Swift 系列指纹驱动包
2. 自训练嵌入网络（备选；基础设施已就绪）
3. 接受 NCC 的 FAR 风险（不可上线，仅研究）

注：EH577 作者的 NCC 匹配器大概率存在同样的 FAR 问题（其未发表
同人异指测试数据）。

## 8. 稳定性工程成果（真机验证）

1. 校准链路（读校准→复位→上传→POST_CAL 轮询）稳定出图
2. claim 配额回收 + 校准重传：从 6 帧/claim 放宽到 200（每 130ms 一次
   重传的重压 3.5 分钟内 1865 次导致固件挂死）
3. 采集结束关闭序列（topni1 POST_REPEAT，含 AGC/曝光 `71` 族）：
   防止传感器滞留连续采集模式导致按压失灵（今天两次复现）
4. 幻影在检恢复：背景刷新门 std<10（EH577 的 raw<200 门在 EH575 永假）
   + 无条件 4 秒 stuck-presence 看门狗
5. 优雅关闭（延迟到采集循环收尾再释放接口）+ SIGINT 化测试脚本
6. USBDEVFS_RESET 软复位（scripts/reset-sensor.sh）从端点残留/挂死恢复
7. 帧读取挂死时 2s 超时不触发、SIGINT 链失效 → 只能 kill -9 + 复位，
   根因与固件疲劳相关，关闭序列（第 3 条）为主要缓解

## 9. 开放问题（已回答项存档）

1. ~~EH575 有效宽度：70 还是 103？~~ **已回答（2026-09-12 数据集分析）：103，无死区。**
   600 帧列活跃度分析：全部 103 列非零率 100%、跨帧 std 11–20；EH577 的 33 列
   死区在 EH575 不存在。`EGIS0575_ACTIVE_WIDTH` 默认值即正确。
2. ~~EH575 无校准初始化（EH577 路线）是否可行？~~ **已回答（2026-09-12 真机探测）：不可行。**
   PRE_INIT/POST_INIT 全部正确应答、`64 14 ec` 稳定回 5356 字节，但帧内容全零；
   校准上传是 EH575 出图的必要条件。另证实 `73 14 ec` 裸发（不跟 5356 字节数据）
   第一次得 507ms 全零响应、第二次直接挂死传输——校准版驱动已把 PRE_INIT
   从默认路径退役（仅 EGIS0575_SKIP_CALIBRATION=1 时用于 A/B）。
3. ~~claim 大读配额~~ **已验证**：配额存在，回收后校准重传恢复，20 秒 156 次
   回收零超时。
4. **presence 阈值 18% 直接适用**（2026-09-12 数据集：无指帧 coverage 最高 17%
   vs 手指帧最低 19%，边界干净；56 指/450 空帧）
5. **质量门真手指通过率 86%**（48/56），失败帧均为 minutiae=0（糊帧正确拒绝）。
   注意 EH575 空帧满幅低强度内容（raw_nonzero=5356），raw-finger-pixels
   判据无区分度，coverage 是唯一有效判据（已记录 protocol.md §6）。
6. **图像质量评估**（视觉）：脊线清晰、覆盖 ~95%、噪声中等偏轻，1:1 匹配可用。
7. NCC 阈值 0.50/命中 2 在 EH575 上的 FRR/FAR 曲线 —— **进行中**（enroll/verify 闭环）
8. identify 能否安全启用（1:N，画廊数量上限）
